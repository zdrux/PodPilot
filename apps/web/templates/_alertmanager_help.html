Sending cluster · Alertmanager

How to configure Alertmanager

Uses your current cluster login for read-only checks against the saved connector. Secret-read permission is required. No configuration or token values are displayed.


    

    
1. Prepare this connector

      
Save this cluster connector with its webhook token, read-only cluster credential, and admitted alert names, then enable it. Copy the newly generated token before leaving the form. Saved tokens are not displayed or returned.

      {% if not selected %}
Save the connector first. Reopen this help afterward to get its assigned receiver path. Do not use SAVE_CONNECTOR_FIRST as an ID.
{% endif %}
      
Replace PODPILOT_HOST below with PodPilot's HTTPS hostname reachable from the sending Alertmanager. Use this connector only for alerts from its registered cluster. The webhook path must accept bearer authentication without an interactive login redirect.

    

    
2. Locate each sending Alertmanager configuration

      
For OpenShift platform monitoring, edit the decoded alertmanager.yaml key in Secret openshift-monitoring/alertmanager-main. If a separate user-workload Alertmanager is enabled, its configuration is in openshift-user-workload-monitoring/alertmanager-user-workload. Configure the instance that actually routes these alerts; do not enable a second sender unnecessarily.

      
For standalone Alertmanager, edit its configured YAML file. For Helm or GitOps-managed installations, update the owning configuration instead of editing generated Pods. Back up the existing configuration and merge the following additions; these snippets are not replacement files.

    

    
3. Add a receiver to receivers

      
Append this entry to the existing top-level receivers list. Replace PASTE_WEBHOOK_TOKEN with the exact token saved in PodPilot, without a Bearer prefix. Keep the resulting secret configuration out of Git and logs.

      
# Append to receivers:
- name: podpilot
  webhook_configs:
    - url: "https://PODPILOT_HOST/api/v1/incident-webhooks/{{ selected.id if selected else 'SAVE_CONNECTOR_FIRST' }}"
      send_resolved: true
      http_config:
        follow_redirects: false
        authorization:
          type: Bearer
          credentials: "PASTE_WEBHOOK_TOKEN"

      
If a receiver named podpilot already exists, update it rather than adding a duplicate. Alternatively, use credentials_file instead of credentials when the token is mounted from a Secret; the path must exist inside every Alertmanager replica.

    

    
4. Route critical alerts to PodPilot

      
Insert this as the first child of the existing root route.routes, before routes that stop matching. Keep the root receiver, existing sibling routes, inhibition rules, and other settings.

      
# First entry under route.routes:
- receiver: podpilot
  matchers:
    - 'severity="critical"'
  group_by: [alertname]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  continue: true

      
continue: true allows later sibling routes to deliver their existing notifications. It does not also notify the parent receiver. If you rely on the root receiver as a fallback, add a final catch-all child using that same receiver name:

      
# Last entry under route.routes, when needed:
- receiver: EXISTING_ROOT_RECEIVER_NAME

      
This forwards critical alerts; PodPilot accepts only names in this connector's saved Admitted alert names. Resolved notifications are required to close incidents. Sending the same cluster's alerts through multiple connectors can create duplicate incidents.

    

    
5. Configure trust and apply

      
Keep certificate verification enabled. For a private CA, mount the CA bundle into Alertmanager and add the following beneath the receiver's http_config:

      
tls_config:
  ca_file: /etc/alertmanager/secrets/podpilot-webhook-ca/ca.crt

      
For OpenShift platform monitoring, create Secret podpilot-webhook-ca with key ca.crt in openshift-monitoring, and add its name to alertmanagerMain.secrets in the config.yaml key of ConfigMap cluster-monitoring-config. Preserve the existing secret mounts. Other installations need their own supported mount configuration.

      
Validate the complete merged file using an amtool version matching your Alertmanager:

      
amtool check-config alertmanager.yaml

      
Save the merged YAML through its Secret or deployment configuration. OpenShift's monitoring operator reloads the managed configuration; for standalone Alertmanager, use its configured reload mechanism. Check configuration reload status and notification errors.

    

    
6. Verify delivery

      
Use a controlled critical test alert whose name is admitted for this connector, then resolve it. Confirm the incident appears in PodPilot, its receiver's Last accepted timestamp updates, and the resolution arrives. This can start an investigation. Test & discover checks connector access; it does not test Alertmanager delivery.

      
HTTP 401 indicates an invalid token or disabled/missing receiver; a login redirect indicates front-door routing/authentication needs correction. HTTP 202 alone does not prove an incident was created: a non-admitted alert can be acknowledged and ignored. TLS errors require correcting certificate trust or hostname; timeouts require checking sender reachability.
